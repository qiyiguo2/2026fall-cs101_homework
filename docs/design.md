# 英语词汇发音练习平台 · 设计文档
## 1. 项目目标
结合pku 课程 《美国英语语音与听说词汇》教学，一个面向学生的，练习通过听力区分相似发音的重难词汇，以及单词发音的程序/平台（用来代替那个我安装不了的e-primer的）

## 2. 范围
### MVP（本次要做）
- [ ] 近似音区分-test：
	-开始：用户选择一组想要练习的近似音（如元音/i:/与/ɪ/，一般是两个一组，极少数是三个一组），指定练习的题目数量x，决定进行单词练习还是句子练习：
	-进行（以单词练习为例）：一次测试由x道选择题组成，每道题由系统在题库内随机抽取一组单词，将两个单词标上编号展示在屏幕上，同时随机播放其中一个单词的音频，用户需在t秒内（t默认为1，可以在设置中调整）按下键盘上的1或2进行选择，选择后系统给出选择的对错，否则就显示无回答，然后立刻进行下一题。如此循环直到结束。
	-结束与反馈：练习结束后，给出用户总共的练习题目数量，正确数，错误数，并且用户可以再次查看自己做过的各题。
	
- [ ] 看读译test
	-开始：用户决定自己想要练习的题目数量（默认为20）然后开始
	-进行：在词库中随机抽取20个单词在屏幕上依次展示，展示两轮：
		第一轮：每个单词展示一秒，同时设备录音，录制用户朗读单词的声音
		第二轮：每个单词展示5秒，不录音，要求用户用键盘输入该单词中文译文的任意一项
	-结束与反馈：练习结束后，给出用户总共的练习题目数量，各题翻译的正确与否，以及各个单词的正确翻译。并且允许用户回放自己的朗读音频，并且与标准的朗读音频做对比
- [ ] 听读写test
- [ ] -开始：用户决定自己想要练习的题目数量（默认为20）然后开始
	-进行：在词库中随机抽取20个单词，依次播放音频，展示两轮：
		第一轮：播放单词音频后空出一秒，同时设备录音，录制用户朗读单词的声音
		第二轮：播放单词音频后空出5秒，不录音，要求用户用键盘输入该单词的正确拼写
	-结束与反馈：练习结束后，给出用户总共的练习题目数量，各题拼写的正确与否，以及各个单词的正确翻译。并且允许用户回放自己的朗读音频，并且与标准的朗读音频做对比：
	<mark>iOS Safari 不支持 MP3 编码，录音时需要回退为 WAV 格式</mark>
### 暂不做（V2 候选）

- 课堂考试功能
- 扔个发音词典进去
- 发音重难点讲解
- 好看的UI

## 3. 技术选型

| 层            | 选型                                                         | 理由                                                 |
| ------------ | ---------------------------------------------------------- | -------------------------------------------------- |
| **前端**       | 原生 HTML/CSS/JS + **Bootstrap 5**（CDN 引入）                   | 零构建配置，组件开箱即用，适合快速交付；录音用 MediaRecorder API，桌面端兼容性足够 |
| **后端**       | Python + **Flask**（或 FastAPI，选你最顺手的）                       | 你已明确最熟 Python；Flask 轻量，适合这种小型 API 服务               |
| **数据库**      | **SQLite**（MVP 阶段）                                         | 单文件、零运维、单服务器场景完全够用；未来并发写入增多时可平滑迁移到 PostgreSQL      |
| **音频存储**     | **服务器文件系统**（`/var/www/audio/`），数据库只存路径                     | 避免二进制大对象拖垮数据库；Nginx 直接托管静态音频，后端只处理逻辑               |
| **部署**       | PKUCLab 云主机 + **Docker**（运行 Flask）+ **Nginx**（反向代理 + 静态文件） | 环境隔离、部署可复现；Nginx 负责 SSL 和静态资源，Flask 专注业务逻辑         |
| **域名/HTTPS** | 先用ip地址访问                                                   | 动态应用不能用 GitHub Pages 托管；先用 IP 访问跑通，域名作为后期优化        |
MVP 阶段以“跑通核心功能”为优先。前端不引入 React/Vue，用原生 JS + Bootstrap 减少构建复杂度和学习成本；数据库从 SQLite 起步，避免初期运维 PostgreSQL 的负担；音频文件与元数据分离存储，数据库只保存路径，文件由 Nginx 直接托管。所有选型均可在未来按需升级（SQLite → PostgreSQL，Bootstrap → 更定制化的方案），不影响 MVP 交付。
